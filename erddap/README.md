# The central ERDDAP

> **For maintainers.** Data managers never edit anything here.

The central node holds **no data**. Every federated dataset is an
`EDDTableFromErddap` or `EDDGridFromErddap` proxy that re-serves the regional
ERDDAP it came from, which is what makes the federation a *view* over the
facilities rather than a copy of them.

```
erddap/
├── datasets.xml            GENERATED — do not edit
├── datasets.xml.backups/   timestamped, pruned to keep_backups
├── data/                   /erddapData in the container
│   ├── hardFlag/           touch <datasetID> → reload + discard cached shape
│   └── flag/               touch <datasetID> → reload
├── templates/
│   ├── datasets_header.xml everything before the first dataset
│   └── datasets_footer.xml </erddapDatasets>
├── logo.png, favicon.ico   branding, mounted read-only
└── .env                    ERDDAP tuning
```

---

## `datasets.xml` is a build artefact

It is written by `validation_gate/erddap.py` from **the database**, not from
the results of the current run — so an incremental run cannot drop the datasets
it never looked at.

**Hand-editing it is always wrong.** The next run overwrites it. The generated
file says so in a banner at the top:

```xml
<!-- GENERATED BY THE EMSO VALIDATION GATE - DO NOT EDIT BY HAND.        -->
<!-- The next run overwrites this file. Edit federation/ instead.        -->
```

To change what is in it, change `federation/` (which datasets exist) or
`validation-gate.yaml` (what qualifies).

### Structure

`header + banner + <dataset> blocks + footer`. The header is
`templates/datasets_header.xml` with two placeholders substituted:
`__DATASETS_XML_BUILD_DATE__` and `__DATASETS_XML_COUNT__`.

Each block is deliberately minimal:

```xml
<dataset type="EDDTableFromErddap" datasetID="OBSEA_seabed_station_TS_L1b" active="true">
    <sourceUrl>https://data.obsea.es/erddap/tabledap/OBSEA_seabed_station_TS_L1b</sourceUrl>
    <reloadEveryNMinutes>60</reloadEveryNMinutes>
</dataset>
```

`<defaultGraphQuery>` is added when the registry set `defaultQuery`. All four
values go through `xml.sax.saxutils.escape`, so an ampersand in a query cannot
end the element early. The registry's `defaultQuery` is already
percent-encoded — see [`../federation/README.md`](../federation/README.md) for
why writing `&amp;` there breaks the graph.

### Two safeguards, both learned the hard way

**The generated XML is parsed before it replaces the live file.** A malformed
`datasets.xml` makes ERDDAP *silently keep the previous one*, so the federation
looks fine while being hours stale. On a parse failure the gate raises
`ErddapError` and leaves the live file untouched.

**Every build keeps a timestamped backup** in `datasets.xml.backups/`, pruned
to `keep_backups` (default 10). Rolling back is a copy:

```bash
cp erddap/datasets.xml.backups/datasets.20260929T151100Z.xml erddap/datasets.xml
```

### Two encoding details that bite

**The file is written in place, not via `os.replace`.** It is a bind-mounted
*file* in the ERDDAP container, and replacing the inode would leave the
container holding the old one. A half-written file is the accepted risk; the
parse check before the write is what makes that acceptable.

**Encoding is `ISO-8859-1` with `errors="xmlcharrefreplace"`**, matching the
templates, which are read with the same encoding. Anything outside Latin-1 is
emitted as a numeric character reference.

## Reloading

`reload_method` in [`../validation-gate.yaml`](../validation-gate.yaml) chooses
how a changed dataset is picked up. All three touch only the datasets that
changed — the rest of the federation keeps serving, which restarting ERDDAP or
waiting for `loadDatasetsMinMinutes` does not.

| Method | Effect |
|---|---|
| `hardflag` | touch `data/hardFlag/<datasetID>` — reload **and discard the cached structure**. The default. |
| `flag` | touch `data/flag/<datasetID>` — reload only. Cheaper, correct when only the data behind an unchanged structure moved. |
| `none` | write `datasets.xml` only. For a read-only or dry-run host. |

**Why `hardflag` is the default.** Every dataset here is an `EDD*FromErddap`
proxy, so what ERDDAP caches is the *regional* dataset's variable list. When a
facility adds a variable, a soft flag reloads the dataset while keeping the
stale shape — a dataset that looks reloaded and serves the old structure.

Only datasets **new to the file** are flagged (`current - previous`), computed
by parsing the live file before overwriting it. If that file is missing or
unparseable, `existing_dataset_ids()` returns an empty set and everything is
flagged: noisy, but safer than deploying against a wrong picture of the current
state.

Flagging is best-effort — an `OSError` logs a warning and returns `False`
rather than failing the run. The dataset is in `datasets.xml` either way and
will load within `reloadEveryNMinutes`.

## The container

```yaml
erddap:
  image: erddap/erddap:v2.31.1
  volumes:
    - ./erddap/datasets.xml:/usr/local/tomcat/content/erddap/datasets.xml
    - ./erddap/data:/erddapData
    - ./erddap/logo.png:...:ro
    - ./erddap/favicon.ico:...:ro
```

`datasets.xml` is bind-mounted as a **file**, not by mounting the directory, so
everything else the gate writes under `erddap/` — the backups, the flag
directories — stays out of the container.

**No `user:` is set, deliberately.** This image starts its entrypoint as root
to `chown /erddapData` and then drops to `TOMCAT_USER_ID`; forcing the user
would stop it doing either. `TOMCAT_USER_ID`/`TOMCAT_GROUP_ID` are taken from
`${UID}`/`${GID}` in the root `.env`, so there is one place that says which host
user owns the bind mounts.

The gate shares these bind mounts. That is what lets it write `datasets.xml`
and flag a reload instead of restarting ERDDAP.

Health check: `curl http://localhost:8080/erddap/index.html`, with a 120 s
start period — ERDDAP is slow to boot.

### `erddap/.env`

ERDDAP tuning that does not change between deployments. The base URLs, the SMTP
connection and `ERDDAP_flagKeyKey` are **not** here — they are deployment-wide
and live in the root `.env`, where `gate.py password-rotate` can reach the last
of them.

`ERDDAP_flagKeyKey` is read once at startup, so a rotated value applies on the
next `docker compose up -d erddap`, and every flag URL issued under the old key
stops working. The gate's own file-based flagging is unaffected — it writes to
the flag directory directly and never uses a URL.

## Templates

`datasets_header.xml` carries everything before the first dataset:
`<erddapDatasets>`, the `<requestBlacklist>`, `<subscriptionEmailBlacklist>`,
the user-facing HTML fragments, and the two placeholders. `datasets_footer.xml`
is three lines closing the document.

Edit these to change branding or ERDDAP-level settings; edit `federation/` to
change which datasets exist. A missing template raises `ErddapError` rather
than producing a file — the gate will not invent an ERDDAP configuration.

## Troubleshooting

**A dataset is in `datasets.xml` but not in the catalogue.** ERDDAP rejected
that block. Check `data/logs/log.txt` in the container. The most common cause is
the regional dataset being unavailable when ERDDAP tried to load the proxy;
touch the hard flag to retry.

**Nothing at all loaded after a run.** ERDDAP silently keeps the previous
`datasets.xml` when the new one is malformed — but the gate parses before
writing, so this should be impossible from a gate run. Suspect a hand edit.

**A facility added a variable and it is not showing.** That is the soft-flag
failure mode. Confirm `reload_method: hardflag`, then touch
`data/hardFlag/<datasetID>` manually.

**Everything was flagged for reload at once.** `existing_dataset_ids()` found
the live file missing or unparseable. Harmless, and self-correcting on the next
run.
